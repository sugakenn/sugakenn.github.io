近年のパソコンはノートだけでなくデスクトップでもWi-Fiインターフェースを持つことが多くなりました。

そのようなパソコンで、Windows11稼働の要件に届かないものを有効活用できないかと考え、
hostapdを使って、Wi-Fiのアクセスポイントにしてみました。

また、市販のエントリーモデルのWi-Fiルーターには搭載されないWPA2-エンタープライズの機能をつけてみました。

## Wi-Fiカードの確認

近年はM.2 Wi-Fiカードが搭載されているケースが多いと思いますが、
まず`iw list`コマンドで、搭載されているその仕様を確認します。

アクセスポイントとして使いたい場合は、それによって表示される
`Supported interface modes`の項目に`AP`の記述が必要です。
APはアクセスポイントモードに対応しているという意味になります。

あとは、周波数や利用可能な暗号化の種類、Wi-Fiのバージョンなども表示されますので必要に応じて確認します。


周波数帯は、`Band1`、`Band2`といったようにわかれています。その中の項目に次のような項目の有無によって、対応する規格がわかります。


| 表示                                 | 対応規格               |
| ---------------------------------- | ------------------ |
| `HT Capabilities`                  | 802.11n            |
| `VHT Capabilities`                 | 802.11ac           |
| `HE Iftypes` または `HE Capabilities` | 802.11ax (Wi-Fi 6) |
| `EHT Capabilities`                 | 802.11be (Wi-Fi 7) |

旧規格でいう b や g に対応しているかは、2.4G帯が含まれるBandの`Bitrates`で判断します。

 1 , 2 , 5.5 , 11 Mbps のビットレートが存在していたら、b に対応。
 6～54Mbpsのビットレートが存在していたら　gに対応します。 


5G帯を含めて周波数帯の末尾についていることがある、`no IR` は No Initiate Radiationの略で、この周波数帯は自局から発信してはいけないという意味です。


`iw reg set JP`とすることで設定を日本に設定します(揮発性の設定)。そうして再度`iw list`を実行した時に、`No IR`がついていたらその帯域はAPとしては使えません。

`iw reg get`ではその国の周波数帯の詳細情報が表示されます(この表示は使用可能不可能とは無関係です)。5G帯の屋外使用禁止を意味する`NO-OUTDOOR`、レーダー干渉時の自動周波数切り替えがの必要性`DFS`といった情報がでてきました。

基本的にhostapd側で使用できなくなっていると思いますが、この辺りは法律で定められていますので、自身で確認した上で周波数帯を選択するようにしてください。

## ドライバ

ethtool を使うと、現在使用されているドライバが出てきます。
```
ethtool -i wlp1s0
driver: iwlwifi
version: 6.12.95+deb13-amd64
...
```

(Linux Wireless doumentation)[https://wireless.docs.kernel.org/en/latest/index.html]には、それぞれのドライバの詳細が載っています。本当はDFSなどを動かしてみたかったのですが、残念ながら例示で使おうとした`iwlwifi`はドライバベースで、5G帯域のAP設定ができないものでした。


## hostapd

まずは稼働テストをします。次のように設定しました。
```
# /etc/hostapd/hostapd.conf
# Wi-Fiのインターフェース名
interface=wlp1s0
# ブリッジ接続時のブリッジ名
bridge=br0

# 現在はほぼnl80211でいい
driver=nl80211
# ssid
ssid=Debian-AP
# 国
country_code=JP
# 国をクライアントへ通知
ieee80211d=1
# モード　ここでは a=5G か g=2.4G のみ
hw_mode=g
# 仕様するチャンネル
# hostapdやドライバが対応していれば0指定時に自動で判定する
channel=6

# n 規格
ieee80211n=1

# 他の規格
#ieee80211ac=1
#ieee80211ax=1
#ieee80211be=1

# nの帯域幅設定
# HT40 の表記があれば束ねることが可能
# +時は上位チャンネルを -時は下位チャンネルを使う(チャンネルが端の時は注意)
# 設定しなければ 20MHz
ht_capab=[HT40+]

# QoS nやacの時は特に1を推奨
wmm_enabled=1

# テスト用 WPA2-Personal
wpa=2
wpa_key_mgmt=WPA-PSK
rsn_pairwise=CCMP
# パスワードクォート不要
wpa_passphrase=test12345
```

設定ファイルの文法チェック
```
sudo hostapd -t /etc/hostapd/hostapd.conf
```
稼働(テストモード)
```
hostapd -dd /etc/hostapd/hostapd.conf
```

待ち受け禁止のチャンネルを指定すると次のようなエラーがでます。
```
Frequency 5180 (primary) not allowed for AP mode, flags: 0x30053 NO-IR
```

channel自動指定(0)で、ドライバが検出機能をもっていなかったら次のようなエラーがでます。
```
...
No survey data received
…
```

hostadpdが起動するようになったつながったら、ローカルのワイヤーネットワークとブリッジします。これは好みに合わせてルーティングなどにしてください。
今回のケースでは、最終的に証明書認証にするので、ブリッジでそのまま内側へ入れてしまいますが、hostapdとともにDHCPやntablesなどを使ってルーティング構成にすることも可能です。

今回のテストケースではDebian13を利用していますが、この場合ネットワークを管理する方法が、interfaceファイルでネットワークを設定する`ifupdown`方式と`Network Manager`方式があるので、その両方について説明します。
CUIだとデフォルトはifupdown、GUIだとNetwork Managerになると思います。

どちらの場合もそうですが有線LANとブリッジだけ管理して、Wi-Fiインターフェースの管理はhostapdへ任せます。

そうしないと競合することがあります。

### Network Managerの場合

#### ブリッジインターフェースをネットワークマネージャーで作成します

```
nmcli connection add type bridge ifname br0 con-name br0
```

ブリッジにIPアドレスを割り当てます。
```
nmcli connection modify br0 \
    ipv4.method manual \
    ipv4.addresses 192.168.1.10/24 \
    ipv4.gateway 192.168.1.1 \
    ipv4.dns 1.1.1.1
```

有線インターフェースをブリッジに加えます
```
nmcli connection add type ethernet \
    ifname enp2s0 \
    con-name bridge-slave-enp2s0 \
    master br0
```


既存の有線LANインタフェースへのIP設定は消します。削除時は、
名前を指定する必要があるので、先に確認します。ここでは`nmcli connection show`コマンドで、"Wired connection 1"という名前を得られたと想定しています。

```
nmcli connection show
...
nmcli connection delete "Wired connection 1"
```

#### Wi-Fiインターフェースを管理外に
Wi-Fiインターフェースを管理外にする設定を `/etc/NetworkManager/conf.d/ignore-wifi.conf`へ設置します。

```
[keyfile]
unmanaged-devices=interface-name:wlp1s0
```

これでPCの再起動をすれば差し変わります。

**これらの作業はリモートで操作ではで繋がらなくなることがありますので注意してください**

再起動後、`nmcli device status`の出力が次のようになっていればOKです。
確認するポイントは、ブリッジにIPがついているか、有線LANがブリッジに組み込まれているか、Wi-Fiインターフェースが管理から外れているかです。
```
DEVICE   TYPE      STATE       CONNECTION
br0      bridge    connected   br0
enp2s0   ethernet  connected   bridge-slave-enp2s0
wlp1s0   wifi      unmanaged   --

```

ちなみに、Wi-Fiインターフェースをブリッジに組み込む設定は先の、hostapd.confの`bridge=br0`で指定されています。

### ifupdown方式の場合

/etc/network/interfaceファイルでネットワークを管理している場合は、ファイルの中身を後述のようにして再起動するだけです。
バックアップもファイルとして置いておけますので、こちらの方が使い勝手はいいです。

br0には`auto`を指定していますが、allow-hotplugとの違いは、システム起動時にインターフェースをupするautoに対し、allow-hotplugはデバイスを検出したにupします。

brは仮想インターフェスなので、システム起動時にupするのがいいと思います

合わせて設定している`bridge_stp off`は、スパニングツリープロトコルを切っています。
L2で経路ループが起きる心配がなければoffにしておいた方が高速です。

念のためスパニングツリーの設定であるFD(Foward Delay)も0にしておきます。

`static`として設定してた有線インターフェースは`manual`としてアドレス設定をしません。

```
auto br0
iface br0 inet static
    address 192.168.1.10/24
    gateway 192.168.1.1
    bridge_ports enp2s0
    bridge_stp off
    bridge_fd 0

iface enp2s0 inet manual

```

## WPA2-Enterprise(証明書認証)
Personalモードでの接続が確認できたら、freeradiusをインストールして、WPA2-Enterpriseの設定をします。

hostapdの設定のWPA2-Personalの部分を次のように差し替えます。

```
# WPA2-Enterprise
wpa=2
wpa_key_mgmt=WPA-EAP
rsn_pairwise=CCMP

# IEEE 802.1X
ieee8021x=1

# RADIUS authentication server
auth_server_addr=127.0.0.1
auth_server_port=1812
auth_server_shared_secret=test123
```

`wpa_key_mgmt=WPA-EAP`では、WPA2-Enterpriseで 802.1X/EAPを使って認証・鍵管理するという大きな枠組みを指定しています。後続の`ieee8021x=1`の方はhostapdで IEEE 802.1X認証機能を有効化する指定です。
言い換えると、管理方式の設定と、機能の有効化設定です。

`rsn_pairwise=CCMP`でCCMPで暗号化した上で端末ごと(1対1=pairwise)に暗号化しをしていします。RSNの部分ははRobust Security Networkの略で、Wi-Fiを安全に運用するための仕組みを意味しています。

auth_server_addrでfreeradiusサーバーのIP,とauth_server_portでポートradiusのデフォルト値は(1812)を指定しています。

### freeRadiusの設定

#### Authenticatorの設定
radiusはSupplicant、Authenticator、Authentication Serverの三者で構成されます。

Authenticatorはクライアントからの接続要求を受け取り、認証サーバーに確認しにいく役割でhostapdはこの部分を担っています。Authentication ServerがfreeRadiusにあたりますが、まずfreeRadiusにAuthenticatorの設定をします。

この設定は`/etc/freeradius/3.0/clients.conf` に追加します。

```
client hostapd {
    ipaddr = 127.0.0.1
    secret = test123
}
```
secretはhostapdで設定した値と揃える必要があります。ipaddrの部分がローカルホストになっているので少しわかりにくいですが、clients.confにはAuthenticatorのアドレスを指定します。

client の後の`hostapd`は単なる名前です。任意の名前をつけられます。

#### EAPの設定

クライアント(Supplicant)の認証設定はEAPに設定します。EAPはRadiusがサポートする認証方式のひとつで、EAP-TLSという証明書認証をここでは設定します。

この機能はモジュール化されており、freeradius(v3.0)ではその設定を`/etc/freeradius/3.0/mods-available/eap`に記述し、有効化するの時に`/etc/freeradius/3.0/mods-enabled/eap`にそこへのシンボリックリンクを配置する運用となっているようです。

デフォルトでeapは有効になっていますので、今回は手動でモジュールを追加または削除する必要はらいません。

既存の設定ファイル`eap`のバックアップを取った上で書き換えるだけでいいです。


```
eap {
    default_eap_type = tls

    tls-config tls-common {
        # Radiusサーバーの秘密鍵
        private_key_file = /etc/freeradius/3.0/certs/server.key
        # Radiusサーバーの公開鍵
        certificate_file = /etc/freeradius/3.0/certs/server.crt

        # クライアント証明書を発行したCA
        ca_file = /etc/freeradius/3.0/certs/ca.crt

        # クライアント証明書を要求
        require_client_cert = yes
    }

    tls {
        tls = tls-common
    }
    
    # 参考
    #peap {
    #    tls = tls-peap
    #}
}
```

ここでルートレベルに記述してある`eap`はEAP用の設定名なので、固定になります。

tls-config の後に名前をtls-commonという名前をつけて設定を記述しています。

後続の 外側の`tls`はEAP-TLSで使うという意味で、内側の`tls`ではその手前で設定した`tls-config`を指定します。

外側の部分は他には、peap(PEAP-MSCHAPv2など)を指定する場合は、tlsを使う場合はクライアント証明書を要求しませんので、その場合は設定を書き分けて指定します。

この設定後`systemctl restart freeradius`で再起動すれば証明書認証が可能になります。基本的に、指定したCAが署名したクライアント証明書を持つ接続をすべて許可します。

#### 証明書
利用する証明書は、opensshなどで作ります。ここではプライベートCAを作って、freeRadius用のサーバー証明書とクライアント証明書を発行しました。
コツとしては、サーバー証明書はCNとSubjectAltNameをドメイン(FQDN)形式で同名にして作成することです、使えるドメインがなければ架空のものでいいです。
この名前はクライアントで照合される可能性があります。

なくても成立することが多いようですが、長期運用を考えるなら手間でもX.509 v3のEKU(Extended Key Usage)等を指定しておきましょう。
サーバー用なら
```
[ server_cert ]
basicConstraints = critical, CA:FALSE
keyUsage = critical, digitalSignature, keyEncipherment
extendedKeyUsage = serverAuth
```
クライアント用なら
```
[ client_cert ]
basicConstraints = critical, CA:FALSE
keyUsage = critical, digitalSignature
extendedKeyUsage = clientAuth
```
といった感じになると思います。

#### 失効リスト
本格運用するなら、CAで失効リストも作れるように用意しておきましょう。
freeRadiusの先ほどのtls-configの中に次の行を追加します。また、`ca_file`で直接CAの証明書を指定するのではなく、`ca_path`でディレクトリを指定します。
ここでは`/etc/freeradius/3.0/certs/`を意味する`${cadir}`を指定しています。
そのディレクトリ内に、`rootca.crt`と失効リストである`rootca.crl`を配置します。
これらのファイルはそのままの状態では読めないので、`openssl rehash`でファイル名を変換します(正確には証明書や失効リストに対してのシンボリックリンクが作られます)。これは、opensslがIssuerから求めたハッシュで対象のファイルを検索する仕様に合わせるためです。拡張子にも意味があり.0ならCA証明書、.r0ならCRLという意味になります。

```
# ca_fileはやめます。
# ca_file ${cadir}/rootca.crt
ca_path = ${cadir}
check_crl = yes
```

もし既に運用しているCAがあるなら、CAの秘密鍵漏洩対策として、そこから中間CAを作って専用にしておいた方がいいです。


## hostapdの本質

筆者はWi-Fiアプリだと勘違いしていたのですが、もともと、hostapd は、Linuxなどで IEEE 802.11の無線LAN APやIEEE 802.1X Authenticatorを実現するデーモンです。

なので、Wi-Fiに限らず、有線でもその設定が有効です。

ただし、その場合認証を許可した端末だけ通信を通すという部分は、ふたつ以上のNICを用意してnftablesなどで実装する必要があります。Supplicantと対象となるネットワークが直接レイヤ2で繋がっている場合はhostapdサーバーを介さず通信してしまいますので意味がありません。

有線ネットワークに対してhostapdを設定する場合はradius部分はそのまま残し、Wi-Fi設定の部分を次のように差し替えます。

```
interface=enp2s0
driver=wired

ieee8021x=1
```

802.1Xでは特殊な宛先MACアドレスを使用し、Supplicantの初回の接続はIPアドレスなしで接続します(ARPを使わず接続します)。

## 認証ログ

freeRadiusで認証ログを残したい場合は`linelog`を使います。これは先ほどのmodsのひとつでデフォルトで有効になりますが、認証時の出力は設定されていませんので、`/etc/freeradius/3.0/sites-enabled/defaultの`post-auth`の最後のあたりに、`linelog`と記述を入れます。

```
post-auth {
    ...
    linelog
}
```
すると、linelogs設定ファイル中の`filename`で指定した場所に認証ログが出力されるようになります。
